# Подробный аудит проекта: Оценщик книг для Авито (Avito Book Valuer)

## 1. Описание проекта
**Что это:** Веб-приложение (Single Page Application / PWA), предназначенное для быстрой оценки подержанных книг перед выставлением их на Авито. 
**Как устроено:** 
- **Фронтенд:** Написан на React 18, TypeScript и собирается через Vite. Стилизация реализована с помощью Tailwind CSS. Приложение поддерживает PWA (есть `manifest.json` и `service-worker.js`).
- **Бэкенд (отсутствует):** Вся логика выполняется на стороне клиента.
- **Интеграция ИИ:** Использует официальный SDK `@google/genai` для обращения к Gemini API. Модель анализирует фотографии (через камеру или загрузку), распознает метаданные (название, автор, год и т.д.), оценивает предполагаемую стоимость на вторичном рынке и генерирует готовый продающий текст для объявления.
- **Данные:** История запросов и настройки сохраняются локально в браузере с помощью кастомного хука `useLocalStorage`.

## 2. Найденные проблемы и чеклист уязвимостей

Далее приведен список всех найденных недочетов, разделенный на критичные (требуют немедленного исправления, иначе возможны падения или взломы) и некритичные (влияют на чистоту архитектуры и производительность).

### 🔴 Критичные проблемы (Critical)

#### 1. Утечка API-ключа Gemini (Security Vulnerability)
- **В чем суть:** В файле `vite.config.ts` происходит инъекция ключа `process.env.VITE_API_KEY` в глобальную переменную. Поскольку бэкенда нет, этот ключ в открытом виде попадает в бандл клиентской части (в браузер пользователя).
- **Чем чревато:** Любой посетитель сайта может открыть DevTools или исходный код, скопировать ваш платёжный API-ключ Gemini и использовать его в своих целях, исчерпав ваши лимиты и деньги.
- **Меры:** Для стабильного публичного продакшена нужно поднять простой прокси-бэкенд (Express или Serverless функцию), который будет скрывать ключ. Если это сугубо приватный/личный инструмент - риск приемлем, но его надо осознавать.

#### 2. Переполнение LocalStorage (QuotaExceededError)
- **В чем суть:** В `src/App.tsx` история оценок сохраняется в `localStorage` вместе с массивом загруженных изображений (`base64Images`). Строки Base64 картинок могут быть очень "тяжелыми".
- **Чем чревато:** Браузеры ограничивают `localStorage` жестким лимитом в 5 Мегабайт на домен. 2-3 загруженные фотографии быстро съедят этот объем, после чего приложение "упадет" с ошибкой при попытке сохранить очередную историю.
- **Меры:** Хранить картинки в браузере нужно в `IndexedDB` (например, через библиотеку `idb` или `localforage`). Либо сохранять в историю *только текст и оценки*, без самих исходных фото.

#### 3. Tailwind CSS подключен через CDN
- **В чем суть:** В `index.html` используется `<script src="https://cdn.tailwindcss.com"></script>`. 
- **Чем чревато:** В скрипте CDN встроена логика, которая перекомпилирует CSS прямо в браузере "на лету" при каждой загрузке страницы. На продакшене это запрещено: сайт будет загружаться медленнее, могут быть "моргания" нестилизованного интерфейса (FOUC) и проблемы с кэшем.
- **Меры:** Настроить Tailwind через PostCSS (установить как зависимости `tailwindcss postcss autoprefixer` и собирать CSS при билде в `npm run build`).

#### 4. Дублирование исходного кода в корне проекта (Структурный мусор)
- **В чем суть:** В корневой папке лежат клоны множества исходных файлов: `App.tsx`, `index.tsx`, `types.ts` и целые папки `components`, `hooks`, `services`.
- **Чем чревато:** Огромная путаница в импортах. Vite настроен на работу с папкой `src`, но IDE может случайно подхватить корневые файлы. Вы можете отредактировать файл в корне и обнаружить, что проект не поменялся. Проект содержит много мусора.
- **Меры:** Безвозвратно удалить все исходники (`App.tsx`, `components/`, `services/`, `hooks/`, `types.ts`, `index.tsx`) из корня проекта. Весь source-код (исходники) должен располагаться строго в `/src/`.

### 🟡 Некритичные проблемы (Warnings / Tech Debt)

#### 5. Лишний `importmap` в index.html и конфликт версий
- **В чем суть:** В `index.html` прописан `<script type="importmap">`, загружающий React 19 с CDN, в то время как Vite в `package.json` собирает проект на React 18.2.0.
- **Чем чревато:** Сборщик Vite всё равно упакует код из `node_modules`. Importmap в этой архитектуре — бессмысленен, загружает лишний код, и может приводить к рассинхронизациям и ошибкам (multiple React instances).
- **Меры:** Удалить тег `<script type="importmap">` из `index.html`.

#### 6. Потенциальные гонки (Race conditions) с камерой при работе со State
- **В чем суть:** В хуке `CameraModal.tsx` переменная `stream` (поток камеры медиаустройства) сохраняется и отчищается через `useState` и `useEffect` с зависимостью `[stream]`. React обновляет state асинхронно.
- **Чем чревато:** Управление "тяжелыми" нативными API вроде `MediaStream` через стейт React может привести к тому, что при быстром переключении камер старый поток не «потухнет» вовремя (микрофон и диод вебки останутся гореть).
- **Меры:** Использовать `useRef<MediaStream | null>(null)` для мгновенного доступа и гарантии остановки "железа" `track.stop()`. 

#### 7. Отсутствие механизма повторных запросов (Retry-паттерн) к Gemini
- **В чем суть:** Сейчас при коде ошибки `429 Too Many Requests` (частое явление в AI) пользователю выводится красная табличка и предложение попробовать снова вручную.
- **Чем чревато:** Это портит User Experience (UX). При ошибке API лучше попытаться "тихо" повторить запрос 1-2 раза с задержкой, и только потом сдаваться.
- **Меры:** Внедрить логику `retry` в `analyzeBookImage` (например, с таймаутом перед повторной попыткой).
